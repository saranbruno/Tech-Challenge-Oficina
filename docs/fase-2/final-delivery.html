01

Sistema e funcionalidades

Evolução da API da oficina

A Fase 2 amplia o sistema Laravel e PostgreSQL existente com APIs para consulta, aprovação e recusa de orçamentos, comunicação com clientes e operação em Kubernetes.

Ordem de Serviço

A abertura utiliza cadastros existentes, calcula o orçamento no servidor e retorna a identificação da OS. A criação e os registros relacionados são persistidos em transação.

Consulta de status

Administradores consultam a situação por API autenticada com JWT. O cliente utiliza documento e token de acompanhamento para obter uma resposta restrita.

Orçamento e estoque

O webhook assinado por HMAC aceita aprovação e recusa. A aprovação inicia a execução e realiza baixa única do estoque; a recusa cancela a OS sem baixa.

Notificações e fila

Transições persistidas acionam e-mail e SMS conforme os contatos disponíveis. A fila prioriza execução, aprovação, diagnóstico e recebimento; em cada estado, a OS mais antiga vem primeiro.

Fluxo da Ordem de Serviço

Entregue

A recusa do orçamento ou o cancelamento da oficina encerram a ordem no estado cancelada. Estados encerrados permanecem disponíveis para consulta histórica.

Arquitetura

Componentes e implantação

A aplicação mantém as regras de negócio no Domínio. A camada de Aplicação coordena os casos de uso; as interfaces HTTP e os adaptadores de infraestrutura conectam a API aos serviços externos.

Interface HTTP

Rotas, autenticação, validação de entrada e respostas REST.

Aplicação

Casos de uso, resultados e contratos de persistência e integração.

Domínio

Entidades, valores, orçamento e transições da Ordem de Serviço.

Interface HTTP → Aplicação → Domínio

Infraestrutura

Implementações dos contratos: Eloquent e PostgreSQL, JWT, e-mail por Mailpit ou SMTP e SMS por log local ou Twilio configurado.

Desenvolvimento local

Docker Compose executa API, PostgreSQL persistente e Mailpit. O mesmo Dockerfile é utilizado no build da imagem para Kind e CI.

Execução em Kubernetes

Terraform provisiona Kind e Metrics Server. A API usa Deployment e HPA por CPU e memória. PostgreSQL usa StatefulSet e volume persistente.

O cluster local permanece disponível para desenvolvimento. A entrega contínua cria um cluster temporário no runner do GitHub Actions e o destrói ao final da execução.

Escalabilidade e persistência

Uma carga de 120 segundos gerou 4.674 respostas HTTP 200, sem falhas. O HPA elevou a API de uma para quatro réplicas prontas, com métricas de CPU e memória disponíveis. Em verificação separada, o banco preservou dados após a recriação do pod com o mesmo PVC.

O teste de envio SMTP pelo Mailpit passou separadamente. Na validação HTTP, foram recebidos oito e-mails no Mailpit e registrados oito SMS simulados, sem contato com serviço pago.

Segurança e referências

Verificações e documentação técnica

O código e as dependências foram avaliados com Semgrep 1.89.0 e Composer Audit. As credenciais de execução são fornecidas por configuração privada, fora do repositório.

0 achados

O Semgrep executou 114 regras em 287 arquivos rastreados. O Composer Audit não reportou avisos de vulnerabilidade nas dependências verificadas.

Proteção dos contratos

JWT protege os endpoints administrativos; o webhook valida assinatura HMAC sobre o corpo da requisição. Testes verificaram assinaturas ausentes e inválidas.

Limites da análise

Oito arquivos tiveram análise parcial e duas regras excederam o tempo no PDF histórico. A ausência de achados não garante ausência de falhas.
